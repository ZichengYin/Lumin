# 技术方案：为什么是「HTML + 原生 JS」

## 结论

**HTML + 原生 JavaScript + Canvas 2D + Web Audio API。**

不装游戏引擎，不装框架，不装打包工具。项目里一个第三方依赖都没有，`npm install` 是空的。

技术边界很清楚：《余光》需要的东西只有四样——画少量几何图形、精确的时间轴、键盘输入、中文排版。这四样浏览器原生能力全都直接给了，中间再加一层引擎只会增加你需要学的东西。

## 为什么不是别的

| 方案 | 上手成本 | 音游节奏精度 | 中文 / 视觉小说 | 分发 | 判断 |
| --- | --- | --- | --- | --- | --- |
| **HTML + JS + Canvas 2D** | 低。浏览器就是运行时，改一行刷新就见效 | **高**。`AudioContext.currentTime` 是采样级时钟，音游圈标准做法 | 好。Canvas 画字或 HTML 排版都行，中文换行、字体全自动 | 一个 zip，或者一个网址 | ✅ **选它** |
| Python + pygame | 中。要装 Python、装库，还要管虚拟环境 | 中。音频播放和时钟是两套东西，延迟对齐要靠 `pygame.mixer` 的 `get_pos()` 凑，抖动明显更大 | 一般。中文字体要自己找 `.ttf`，换行、标点避头尾都要手写 | 要 PyInstaller 打包成 exe，几十 MB 起步，还常被杀软误报 | ❌ |
| Godot / Unity | 高。要先学编辑器、场景、节点、预制体 | 高 | 好 | 好 | ❌ 你明确说了不用引擎 |
| 直接用 ADOFAN_PIXI 改 | 中。但它是**播放器**，不是游戏 | — | 无 | — | ❌ 见下 |

## 关键技术点

### 1. 时间轴一律用 `AudioContext.currentTime`，不要用 `Date.now()`

这是浏览器音游最容易踩的坑。

- `Date.now()` / `performance.now()` 记的是「墙上时钟」，和音频硬件实际播到哪一帧**没有关系**。音频缓冲区、系统混音延迟会让画面和声音错开 20～200ms，而且随机器变化。
- `AudioContext.currentTime` 由音频硬件驱动，是唯一能告诉你「现在到底播到第几秒」的时钟。

所以结构是：

```
音频开始播放时记下 audioStartTime（就是 AudioBufferSourceNode.start(when) 的那个 when）
当前曲内时间 = ctx.currentTime - audioStartTime - 偏移
```

**谱面、判定、动画全部由这个「曲内时间」驱动**，`requestAnimationFrame` 只负责「按当前时间把画面画出来」，不负责推进时间。

这条已经实现了，见 [`src/core/clock.js`](../src/core/clock.js)。两个容易做错、而且错了很难查的地方：

**① 开始时刻只有唯一一个真相。** `AudioEngine.play()` 返回音频真正开始的 ctx 时刻，`SongClock` 必须用**同一个值**。不能在别处再读一次 `ctx.currentTime` ——两次读取之间隔的几微秒就是固定的对表误差。

**② 行星角度必须是时间的纯函数，不能累加。** 如果写成 `planetAngle += omega * dt`，每次掉帧、切标签页、GC 停顿的误差都会累加进去，跑几分钟就明显错开，而且**永远回不来**。正确写法是每一帧反算：

```js
planetAngle = targetAngle + direction × TAU × frac(曲内时间 / 每拍秒数)
```

这样掉帧只会让画面卡一下，判定一点都不漂。`tests/clock.test.mjs` 里有一条用例专门用「稳定 240fps / 卡成 5fps / 一步跳过去」三种步长走到同一个时刻，断言结果**完全相等**——就是为了防止有人把实现改回累加式。

### 1.5 偏移校准：为什么不能只靠自动值

`ctx.currentTime` 也不是「你听到的时间」。浏览器把音频交给系统、系统再送到耳机，这中间还有一段。`AudioContext.outputLatency` 给出了这段的估计（通常 5～30ms），代码里拿它当默认值。

但自动值只能到这里为止。剩下的取决于耳机、蓝牙、声卡驱动，**没有任何 API 能测出来**。所以必须给玩家一个手动微调：

| | 做法 | 位置 |
| --- | --- | --- |
| 自动 | `outputLatency`，取不到就退到 `baseLatency` | [`src/audio/audio.js`](../src/audio/audio.js) 的 `hardwareLatencySec` |
| 手动 | `←` `→` 实时调，`Shift` 精调 1ms，HUD 上一直显示当前值 | [`src/main.js`](../src/main.js) |

调好之后存进 `localStorage` 是下一步的事。更讲究的做法是做一个**校准关卡**：放一段固定的 click，让玩家跟着敲十几下，统计平均偏差自动填进去——那是所有音游的标配，比让玩家自己猜数字友好得多。

### 2. 画面用 Canvas 2D，不用 WebGL

《余光》的画面元素数是个位数：一颗砖块、一颗行星、一条轨道、几个字。Canvas 2D 一帧的开销可以忽略。

WebGL（PIXI、Three.js）是给成百上千个精灵准备的，这里是纯粹的自找麻烦。等哪天真需要几千个粒子的光效，再换也不迟——渲染层已经被隔离在 `src/render/` 里了。

### 3. 逻辑必须和渲染、输入、音频解耦

这是唯一一条「现在不做、以后一定后悔」的架构要求。

判定就是纯数学：**给定行星角度和完美角度，算出误差角度**。它不需要知道画布多大、玩家按了什么键、音乐播到哪。

所以 `src/core/judge.js` 是纯函数，能在 Node 里直接跑测试。好处很直接：

- 改判定窗口时，跑一次测试就知道有没有弄坏别的
- 以后做关卡编辑器、做回放、做「这一段的难度曲线」，都能复用同一份代码
- 你和 AI 协作时，纯函数是最容易被验证、也最不容易被改坏的形状

`src/core/` 现在有四个文件，全都不碰浏览器，全都能单测：

| 文件 | 负责 |
| --- | --- |
| `geometry.js` | 角度 / 向量 / 极坐标 |
| `judge.js` | 角度差 → 判定等级 |
| `clock.js` | 曲内时间 ↔ 拍号 |
| `chart.js` | 谱面模型：砖块坐标、每块转多少度、什么时候该按 |

最新的进度：**86 个用例全绿**。其中 `tests/main.integration.test.mjs` 会搭一套假的浏览器环境（假 canvas、假 `AudioContext`、假 `fetch`、手动驱动的 `requestAnimationFrame`），把**真实的 `main.js` 原样跑起来**，逐块走完整个关卡——因为「接线」的地方最容易错，而它偏偏是最难测的。

### 4. 输入延迟

- 用 `keydown` 事件里拿到的时刻，**不要**等到下一帧才处理。当前 demo 在 `keydown` 回调里立刻算角度，就是这个原因。
- 监听 `keydown` 时要跳过 `e.repeat`，否则按住空格会连发。
- 正式版要给玩家一个**校准界面**：放一段固定的 click 音，让玩家跟着敲，统计平均偏差，存进 `localStorage`。这是所有音游的标配。不同耳机、蓝牙音箱的延迟差别可以到 150ms 以上。

## 以后要上 Steam 怎么办

代码一行不用改。套一层 [Tauri](https://tauri.app/)（体积小）或 Electron（生态熟）就能打包成桌面应用。前提还是那条：**逻辑和渲染保持解耦**，因为 Node/桌面的 Canvas 和浏览器的差别只在最外层。

## 美术方向：来自 `动画/` 里你自己的素材

项目根目录的 `动画\` 里放了 6 张 `main1~6.png`（2304×1385，每张 4MB+）。从 `main1` 和 `main6` 几乎一致来看，应该是同一段动画的连续帧。

画面内容是：**黑白网点 / 噪点漫画风**。高对比度，阴影用网点（screentone）和颗粒噪点堆出来，线条是铅笔速写质感，几乎不上色。一个长发少女，面对一个只有白色笑脸（两只眼 + 一道弧）的黑色团块。

这件事改变了两个判断：

### 1. 「全黑画面」要拆成两层来理解

你说的是「全黑画面音游」。看到素材之后，我理解成：

| 层 | 画面 | 依据 |
| --- | --- | --- |
| **音游层** | 纯黑。只有轨道、砖块、行星、判定文字 | 你自己说的「全黑」；节奏游戏也**必须**这样——任何多余元素都会抢走注意力 |
| **视觉小说层** | 黑白漫画。网点、噪点、铅笔线 | `动画\` 里的实际素材 |

这两层不是矛盾，是**对照**：音游部分是「看不见」，视觉小说部分是「看见了」。如果结局分歧正好落在这个对照上，形式本身就参与了叙事。

目前 demo 的配色（[`src/config.js`](../src/config.js) 的 `colors`）走的是第一层，保持不变。

### 2. 素材需要先处理才能进游戏

- **单张 4MB+，6 张就是 26MB。** 直接放进网页会让人等很久。需要压成 webp，或者在构建时生成低分辨率版本。
- **2304×1385 不是 16:9。** 要么裁切/补边，要么在 CSS 里做成 `object-fit: cover` 并接受边缘被裁。
- 如果这 6 张确实是动画帧，**更省的做法是做成精灵图（sprite sheet）或者用 CSS/Canvas 逐帧播放**，而不是 6 个独立大文件。
- 这种高对比度网点图**压缩时要特别小心**：JPEG 的块效应会把网点糊成一片灰。优先用 webp 高质量，或者干脆保留 PNG 但降分辨率。

> 这些我还没动。素材是你的，裁剪和压缩方案要先定风格再谈。
