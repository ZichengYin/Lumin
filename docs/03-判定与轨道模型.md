# 判定与轨道模型

这份文档解释「按空格 → 角度差 → 判定等级」背后的几何。看懂之后
[`src/core/chart.js`](<../src/core/chart.js>) 和 [`src/core/judge.js`](<../src/core/judge.js>)
就没有魔法了。

## 一、轨道模型

### 约定

- 屏幕坐标：**x 向右，y 向下**。所以角度 `0°` 指右、`90°` 指下、`-90°` 指上。
- 砖块 **等距**排列，相邻两块的距离恒为 `2R`，`R` 就是轨道半径。
  在单位坐标里这个距离是 `1`，渲染时再乘屏幕比例。
- 行星绕**当前砖块**匀速公转，半径恒为 `R`（单位坐标里是 `0.5`）。

> 等距是刻意的简化。ADOFAI 的编辑器允许砖块斜着放、间距不同，代价是行星换砖块时
> 半径会跳变。等距换来了恒定半径和连续运动，对「全黑画面」这种要求画面干净的风格更合适。

### 完美点在哪儿

设当前砖块在 `Pᵢ`，下一砖块在 `Pᵢ₊₁`。**行星转到两点中点 `Mᵢ` 的那一瞬间就是完美时刻。**

为什么是中点？因为

```
|Mᵢ − Pᵢ| = |PᵢPᵢ₊₁| / 2 = R
```

**中点恰好落在轨道圆上。** 这不是巧合，是 `2R` 这个距离的含义。

于是「完美按下时的极角」就是从本砖块指向下一砖块的方向：

```
θ*ᵢ = 方向(Pᵢ → Pᵢ₊₁) = dᵢ
```

### 到达之后

行星从 `Mᵢ` 切换到**绕 `Pᵢ₊₁` 公转**，半径仍是 `R`。由于 `|Mᵢ − Pᵢ₊₁| = R`，
切换前后位置**严丝合缝**，画面上看不到任何跳变。

这条性质由 `tests/chart.test.mjs` 里的「跨砖块的位置连续性」钉死：测试分别用
「上一段」和「下一段」的公式算出交接点的世界坐标，断言两者之差小于 `1e-12`。

## 二、每块砖要转多少度

设：

```
d_prev = 上一段的方向（砖块 i−1 → i）
d_next = 本段的方向（砖块 i → i+1）
```

行星从上一个完美点 `Mᵢ₋₁` 绕 `Pᵢ` 转到本段完美点 `Mᵢ`。这两个点的方向分别是：

```
方向(Pᵢ → Mᵢ₋₁) = d_prev + 180°
方向(Pᵢ → Mᵢ)   = d_next
```

所以只要知道「朝哪个方向转」，转过的角度就定了：

```js
// direction = +1（极角递增）
sweep = wrap360(d_next − (d_prev + 180))
```

**行星永远朝同一个方向转**（`direction`），结果落在 `(0°, 360°)` 开区间。
这和 ADOFAI 一致——它的 `CalculationExtensions.ComputeStartRotation` 里就是一段
`while` 循环把起点一路推到终点，只有 Twirl 事件才会改变 `clockwise`。

| 转向 | 转过 | 手感 |
| --- | --- | --- |
| `0°`（直线前进） | `180°` | 半圈 |
| `−90°` | `90°` | 急弯，转得少 |
| `+90°` | `270°` | 缓弯，转得多 |
| `±180°`（原地掉头） | `0°` | **禁止**，见下 |

### 为什么禁止掉头

`d_next = d_prev + 180°` 会让转过角度变成 **0**：行星已经站在下一个完美点上了，
玩家没有任何反应时间。`buildChart()` 会直接抛错拒绝这种谱面，并说明原因。

`tests/chart.test.mjs` 里有一条用例专门用暴力搜索验证「转过 sweep 度之后正好落在
目标方向」，不依赖上面这个公式的推导是否正确。

## 三、两种配速方式

转过多少度定了，但**花多少时间**是另一个选择。谱面的 `timing` 字段控制它：

### `timing: "auto"` —— ADOFAI 的做法

时长由转角推出来：

```
beats = sweep / 180        ← 每拍正好转 180°
```

结果：**角速度恒定为每拍 180°**，行星匀速旋转，直线慢、急转弯快。
这条公式和 Circle 里 `GetRelativeDuration` 完全一致：

```csharp
return 60000 / bpm * Math.Abs(oldRotation - newRotation) / 180;
```

### `timing: "uniform"` —— 每块砖固定拍数

```
beats = beatsPerTile        ← 默认 1 拍
```

落点整齐（每一拍一块砖），代价是**角速度随转角变化**：转 90° 的砖块角速度只有
转 180° 的一半。

### 该选哪个

| | 画面 | 节奏 | 适合 |
| --- | --- | --- | --- |
| `auto` | 行星匀速，好看 | 落点由几何决定（通常是 16 分音符网格） | 想做出 ADOFAI 那种手感 |
| `uniform` | 角速度随弯道变化 | 落点整齐、可控 | 想让每一块砖踩在音乐的拍上 |

当前的 `levels/level01.json` 用的是 `uniform`，因为这样最容易验证「判定跟着音乐走」。
单块砖还可以用 `beats` 字段单独覆盖。

## 四、判定窗口

窗口的原始单位是**角度**：

| 等级 | 角度差 |
| --- | --- |
| PERFECT | ≤ 22.5° |
| GOOD | ≤ 45° |
| OK | ≤ 90° |
| MISS | > 90° |

换算成毫秒要用**那一段自己的转速**：

```
该段转一圈的毫秒数  msPerTurn = 360 × beats × (60000 / bpm) / sweep
时间差              ms       = 度 / 360 × msPerTurn
```

于是：

- **`auto` 模式下 `msPerTurn` 恒为 `2 × 每拍毫秒`**（因为 `sweep = 180 × beats`），
  所以判定窗口在毫秒上是**恒定的**。120 BPM 时 ±22.5° = ±62.5 ms。
- **`uniform` 模式下 `msPerTurn` 随砖块变化**，窗口也跟着变。当前关卡实测：

  | 那块砖的转角 | 一圈 | ±22.5° 等于 |
  | --- | --- | --- |
  | 90° | 2000 ms | ±125 ms（宽松） |
  | 180° | 1000 ms | ±62.5 ms |
  | 270° | 667 ms | ±41.7 ms（严格） |

也就是说 `uniform` 下**急转弯反而更宽松**——因为同样的角度差占了更多时间。
这是角度制判定的必然结果，不是 bug。想要各块一致就用 `auto`。

### 角度差的算法

按下瞬间行星的极角是 `θ`，**角度差**定义为「沿公转方向，从 θ 转到 θ* 还要转多少」。
实现见 `judgeHit`：

```js
const travel = Math.sign(omega) || 1;              // 公转方向：+1 或 -1
const raw    = (targetAngle - planetAngle) * travel;
const along  = ((raw % TAU) + TAU) % TAU;          // 规整到 [0, 2π)

// along ≈ 0      → 正好踩在完美点上
// along 是个小正数 → 还差一点才到，按早了
// along 接近 2π   → 刚刚越过去，按晚了
const signed = along <= Math.PI ? along : along - TAU;
```

| `signed` | 含义 | 显示 |
| --- | --- | --- |
| `≈ 0` | 正好 | `+0.0°` |
| 小正数 | 还差一点，**按早了** | `+13.4°` |
| 小负数 | 已经越过，**按晚了** | `−13.4°` |

**为什么不能直接相减**，两个必须一起解决的问题：

1. **转圈会绕回。** `−170°` 和 `170°` 其实只差 `20°`，直接相减得到的是 `340°`。
2. **早晚会撞车。** 玩家「按早了 340°」和「按晚了 20°」在体感上是同一件事——
   行星绕了一圈又回来了。所以要取**离完美点最近的那一次**。

`(along <= π ? along : along - TAU)` 一句同时解决这两件事。超出 `180°` 本来就是
MISS，怎么算都不影响判级。

`travel` 那个乘号是为了让「顺时针」和「逆时针」两种情况下**正数永远表示早**。
测试里 `公转方向反过来，早晚符号不能跟着翻` 就是在钉死这个行为。

> **浮点坑**：角度在「度 → 弧度 → 度」往返一次会带上 `1e-15` 量级的误差，
> 正好等于 `22.5` 的一次按键会算成 `22.500000000000004` 掉进 GOOD。
> `classify` 里加了 `1e-9` 容差（`EPS`）。
>
> 还有一处**边界竞态**：`classify` 用 `<=` 接受窗口边界，所以自动 MISS 必须严格
> 发生在窗口**之后**，否则正好卡在边界上的一拍会因为 `0.5` 算成 `0.5000000000000001`
> 被抢先判成漏掉。`autoMissIfNeeded` 里也加了 `1e-9` 容差。
> 这两个都是跑测试时抓出来的。

## 五、和 ADOFAI 的对照

| | 本作 | ADOFAI / Circle |
| --- | --- | --- |
| 砖块间距 | 恒定 `2R` | 可不同 |
| 公转方向 | 恒定（`direction`） | 恒定，Twirl 事件翻转 |
| 每块砖的时长 | `uniform` 固定 / `auto` 由转角推出 | 由转角推出（`sweep / 180`） |
| 判定单位 | 角度 | 角度 |
| 禁止掉头 | 是 | 是 |
